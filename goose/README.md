# Gooseberry Goose distribution

`version` and `source-commit` pin the unchanged upstream `aaif-goose/goose` release and exact source commit. The release workflow verifies the cloned `HEAD` against `source-commit` and publishes `GOOSE-PROVENANCE` alongside the archives and `SHA256SUMS`. The workflow publishes standard Linux CLI archives for x86_64 and aarch64. From the Gooseberry checkout, run `sudo ./goose/install-goose.sh`. It installs `/usr/local/bin/goose` and copies agents and the browser skill into the technical user's standard Goose configuration directory. Set `GOOSE_HOME` explicitly when using another technical user's home. Until the remote is renamed, the default distribution repository intentionally remains `miloszkolber/pixie`. Override it with `GOOSE_REPOSITORY` after the remote cutover.

Run `./scripts/setup-deployment.sh /absolute/project-root /absolute/data-root` as the non-root technical user after installation. It creates or synchronizes `~/.config/goose/gooseberry.env` mode 0600 with the Goose secret, browser URL, and browser token. This deliberately ignores a non-default `XDG_CONFIG_HOME` because the user unit has the static `%h/.config/goose/gooseberry.env` `EnvironmentFile`. Then install the user unit and start it with `systemctl --user daemon-reload && systemctl --user enable --now goose.service`. The installer never installs or enables the service. Rerun setup after credential rotation.
